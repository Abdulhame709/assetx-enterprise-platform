# خطة استمرار تطوير منصّة AssetX

> **نوع الوثيقة:** خطة تنفيذ مقترحة بعد خط الأساس الحالي
> **التاريخ:** 16 أغسطس 2026
> **الحالة:** مقترح يحتاج اعتماد المستخدم قبل بدء نطاق جديد
> **الفرع المرجعي:** `main`
> **الالتزام المرجعي المفحوص:** `48faaee` — `feat: extend controlled Excel imports for master data`

## 1. القرار التنفيذي المقترح

تستمر المنصّة من خط الأساس الحالي عبر مسارين متتابعين، لا عبر إضافة وحدات جديدة عشوائياً. يبدأ المسار الأول بإغلاق **بوابة الجاهزية التشغيلية للإنتاج**؛ فالنسخة الحالية اجتازت بناء الواجهة والخلفية والاختبارات الأساسية، لكنها لا تزال تعتمد على PGlite محلياً عند غياب `DATABASE_URL`، وتحتاج PostgreSQL مُداراً، وأسرار JWT إنتاجية، وترحيلات واختبار دخان بعد النشر. بعد تثبيت بيئة تشغيل حقيقية، ينتقل المسار الثاني إلى تعميق الوحدات الموجودة في الويب، مع أولوية للتقارير والبحث والإدارة بدلاً من فتح وحدات كبرى جديدة.

هذه الوثيقة لا تعتمد قراراً معمارياً جديداً ولا تنفذ تغييراً في قاعدة البيانات. أي تغيير Schema أو توسعة نطاق كبيرة يجب أن يمر أولاً عبر طلب تغيير أو RFC، ثم ADR معتمد، ثم تصميم واختبارات وترحيل قابل للرجوع، وفق قواعد المشروع.

## 2. نقطة البداية المثبتة

| المجال | الحالة الحالية | أثرها على الخطة |
|---|---|---|
| المستودع | الفرع `main` نظيف ومتزامن مع `origin/main` عند `48faaee` | يمكن إنشاء فرع عمل جديد من هذا الالتزام دون إعادة تأسيس المشروع |
| الخلفية | NestJS مع Clean Architecture، JWT/RBAC، تعدد مستأجرين، أصول، جرد، حركات، صيانة، تقارير، تدقيق، بحث، واستيراد منضبط | لا حاجة لإعادة بناء النواة؛ التركيز على التكامل والعمق التشغيلي |
| الواجهة | Next.js App Router مع غلاف مؤسسي عربي، صفحات الأصول والجرد والصيانة والحركات والبيانات الأساسية والاستيراد | بعض المسارات موجودة لكنها سطحية، خصوصاً التقارير والبحث والإدارة |
| الاختبارات | تحقق موثق لبناء الخلفية والواجهة، اختبارات Backend وWeb، ونجاح CI الأخير | يجب إعادة تشغيل بوابة كاملة بعد التزامات الاستيراد وإعادة التصميم الأخيرة |
| قاعدة البيانات | PGlite محلياً، مع مخطط PostgreSQL وترحيلات جاهزة | النشر العام محجوب حتى توفير PostgreSQL مُدار وتطبيق الترحيلات |
| الجاهزية | مرشح إصدار لبيئة نشر مراقبة، وليس إنتاجاً عاماً بعد | الأولوية الأولى تشغيلية وليست إضافة ميزة جديدة |
| الديون المؤجلة | async jobs، BullMQ/Redis، S3، retention، materialized read models، SaaS/billing | تبقى خارج النطاق ما لم يتحقق محفزها أو يعتمدها المستخدم صراحة |

## 3. ترتيب الأولويات المقترح

### المرحلة صفر: إعادة تثبيت خط الأساس وقفل الإصدار

**الهدف:** التأكد من أن آخر دفعة، بما فيها الاستيراد المنضبط للبيانات الأساسية وإعادة التصميم المؤسسي، قابلة للبناء والاختبار والتراجع.

ينبغي إنشاء فرع عمل باسم واضح، ثم تشغيل بناء الخلفية، اختباراتها على دفعات عند الحاجة، بناء الواجهة بإعداد الإنتاج، اختبارات Vitest، وفحص المسارات الأساسية مع جلسة حقيقية. يجب أيضاً تحديث سجل التحقق ليشير إلى الالتزام `48faaee` بدلاً من الاكتفاء بنتائج التحقق السابقة عند `0322fc3`.

**معيار الإغلاق:** لا أخطاء TypeScript أو lint أو build، نجاح الاختبارات الآلية، تحقق يدوي من تسجيل الدخول، الأصول، الحالات، الاستيراد، الصيانة، الحركات والجرد، وتسجيل نتيجة مرئية عربية متجاوبة.

### المرحلة الأولى: تأسيس النشر والإنتاج

**الهدف:** تحويل المرشح الحالي إلى بيئة تشغيل مراقبة قابلة للاعتماد.

يشمل ذلك توفير PostgreSQL مُدار، تطبيق الترحيلات والـ seed بطريقة قابلة للتكرار، ضبط `DATABASE_URL`، `CORS_ORIGIN`، `JWT_ACCESS_SECRET` و`JWT_REFRESH_SECRET` خارج المستودع، وتثبيت مسار نشر منفصل للواجهة والخلفية. بعد ذلك ينفذ اختبار دخان بحساب اختبار مستقل يغطي الصحة، تسجيل الدخول، المستأجر، قراءة وإنشاء أصل، حالات الأصول، الصيانة، الجرد، الاستيراد، والتدقيق.

ينبغي كذلك توثيق النسخ الاحتياطي والاستعادة، نافذة الاحتفاظ، مؤشرات الصحة، تنبيهات فشل الخدمة، ومراقبة أخطاء المصادقة وقاعدة البيانات. لا تُنفذ هذه الخطوة عبر أسرار تجريبية أو قاعدة PGlite محلية.

**معيار الإغلاق:** نشر ناجح على PostgreSQL مُدار، ترحيلات موثقة، أسرار إنتاجية فريدة، اختبار دخان أخضر، وخطة استعادة مجرّبة أو موثقة مع مسؤول ووقت استجابة واضح.

### المرحلة الثانية: إكمال تجربة الويب ذات القيمة الأعلى

**الهدف:** رفع الوحدات الموجودة من صفحات عرض أولية إلى أدوات مؤسسية قابلة للاستخدام اليومي، دون إعادة بناء الواجهة من الصفر.

تبدأ الأولوية بوحدة **التقارير**. الخلفية تحتوي عقوداً واختبارات للتقارير والقوالب والتقارير المجدولة، بينما صفحة الويب الحالية تعرض مؤشرين وزر تصدير CSV للأصول فقط. لذلك تُبنى واجهة اختيار نطاق التقرير ومصدر البيانات والفترة والفلاتر، ومعاينة النتائج، واختيار CSV/XLSX/PDF، وحفظ القالب، مع إظهار حالات التحميل والنجاح والفشل والصلاحيات بوضوح. أما الجدولة والإرسال بالبريد فتُطرح كقرار مستقل إذا احتاجت بنية وظائف خلفية أو مزود بريد.

بعد التقارير تأتي وحدة **البحث**. تُربط الواجهة بقدرات البحث المتقدم والبحث المحفوظ الموجودة في الخلفية، مع فلاتر الموقع والنوع والحالة والموظف، حفظ البحث واستعادته، ورابط نتيجة قابل للمشاركة داخل المستأجر من دون تجاوز الصلاحيات.

ثم تُستكمل **الإدارة** تدريجياً: المستخدمون، الأدوار، الصلاحيات، والمستأجر الحالي، مع حواجز `adminProcedure` أو ما يعادلها في الخلفية، ومصفوفة صلاحيات واضحة في الواجهة، وسجل تدقيق لكل تغيير حساس. تبقى الإعدادات العامة البسيطة منفصلة عن إدارة الهوية والصلاحيات.

**معيار الإغلاق:** كل وحدة لها تدفق مستخدم مكتمل، حالات فارغة وتحميل وفشل، صلاحيات محكومة، اختبارات API وواجهة، مراجعة عربية متجاوبة، وتوثيق عقد الاستخدام.

### المرحلة الثالثة: تعميق التشغيل الميداني

**الهدف:** تحويل الجرد والصيانة والحركات إلى تدفقات تشغيلية متكاملة مع التقارير والتدقيق.

يركز العمل على تحسين تجربة الجرد الميداني، عرض الفروقات والاقتراحات القابلة للتفسير، اعتماد المراجعة البشرية، ثم ربط النتائج بالتقارير وسجل التدقيق. تُضاف أي قدرات Offline أو مزامنة جديدة فقط بعد اختبار التعارضات وإعادة المحاولة وفقد الاتصال على أجهزة فعلية أو محاكاة موثوقة. في الصيانة والحركات، تُراجع دورة الحالة، الصلاحيات، الرسائل العربية، وسجل الأحداث عبر السيناريوهات الفعلية لا عبر الواجهة وحدها.

**معيار الإغلاق:** سيناريوهات قبول مكتوبة ومجتازة من إنشاء الدورة حتى الإغلاق، مع نتيجة قابلة للمراجعة لكل فرق أو اقتراح، وعدم وجود انتقال تلقائي غير مصرح به للأصل أو الحركة.

### المرحلة الرابعة: التقوية المؤسسية حسب المحفزات

**الهدف:** معالجة الديون المؤجلة عندما تظهر الحاجة التشغيلية الفعلية.

لا يبدأ async export أو BullMQ/Redis أو S3 أو أرشفة سجل التدقيق أو read models مسبقاً لمجرد وجودها في السجل. يبدأ كل بند فقط عند تحقق محفزه، مثل تجاوز حجم التصدير حدود الاستجابة، الحاجة إلى ملفات كبيرة أو احتفاظ طويل، ارتفاع حجم سجل التدقيق، أو ظهور حمل يتطلب قراءة محسنة. عند اعتماد أي بند، ينشأ ADR مستقل يحدد النطاق، الكلفة، الفشل وإعادة المحاولة، المراقبة، وخطة الرجوع.

### المرحلة الخامسة: منصة الجوال والتوسع التجاري

بعد تثبيت الويب والإنتاج والتشغيل الميداني، يراجع الفريق تطبيق Android/Offline كمنتج ميداني مستقل، ثم multi-tenant activation والتكاملات والفوترة عند اعتمادها تجارياً. لا تُخلط هذه المرحلة مع إصلاحات الويب الحالية، لأن لكل منها دورة قبول ومخاطر تشغيل مختلفة.

## 4. خطة أول دفعة تنفيذية

| الترتيب | العمل | النتيجة المطلوبة | الاعتماد |
|---:|---|---|---|
| 1 | إنشاء فرع استمرار من `main` وتثبيت الالتزام المرجعي | خط عمل قابل للتتبع | لا يوجد |
| 2 | تشغيل بوابة build/test/lint للخلفية والواجهة | تقرير baseline محدث | توفر Node/npm والاعتمادات |
| 3 | إعداد قائمة متغيرات بيئة النشر والتحقق من عدم تسريب الأسرار | ملف تشغيل آمن دون قيم سرية | اختيار مزود الاستضافة |
| 4 | توفير PostgreSQL مُدار وتطبيق migrations/seeds | قاعدة بيانات بيئة staging | بيانات اتصال فعلية من المستخدم/المضيف |
| 5 | تنفيذ اختبار دخان بعد النشر | إثبات الجاهزية التشغيلية | نجاح البنود 2–4 |
| 6 | توثيق backup/restore والمراقبة | إغلاق بوابة الإنتاج | أدوات الاستضافة والتنبيه |

## 5. معايير العمل الإلزامية لكل ميزة

لا تُعتبر الميزة مكتملة بمجرد ظهور الصفحة. يجب أن يتضمن كل نطاق جديد عقداً واضحاً، حماية مستأجر وصلاحيات، معالجة أخطاء عربية مفهومة، حالات تحميل وفراغ وفشل، اختبارات وحدة وتكامل وواجهة عند الحاجة، بناء إنتاج، ومراجعة مرئية على سطح المكتب والهاتف. وإذا تغيرت قاعدة البيانات، يجب أن يسبق ذلك ADR مع migration وخطة rollback.

| البعد | معيار القبول |
|---|---|
| المعمارية | التزام Clean Architecture وRepository Pattern وعدم وضع SQL أو منطق أعمال في Controller/UI |
| الأمان | JWT/RBAC/permission checks وtenant isolation وعدم كشف بيانات مستأجر آخر |
| البيانات | UUID تقني، business code للعرض/البحث، timestamps متسقة، وسجل تدقيق للعمليات الحساسة |
| الواجهة | عربية RTL فعلية، متجاوبة، قابلة للوحة المفاتيح، مع focus states ورسائل قابلة للفهم |
| الاختبار | unit + integration/e2e بحسب النطاق، ثم build إنتاجي واختبار دخان |
| التوثيق | تحديث backlog وقرار النطاق وملف الإغلاق، دون تعديل صامت لوثائق تاريخية معتمدة |

## 6. ما لن يدخل الدفعة الأولى

لن يبدأ في الدفعة الأولى محرك موافقات عام، ذكاء تنبئي يغير البيانات تلقائياً، حذف مادي للبيانات الأساسية، استيراد استبدالي أو استعادة قاعدة البيانات من الواجهة، فوترة SaaS، أو إعادة كتابة كاملة للواجهة. كما لن تُضاف بنية Redis/BullMQ/S3 إلا بقرار منفصل ومحفز تشغيلي مثبت.

## 7. القرارات المطلوبة من مالك المشروع

المطلوب اعتماد ترتيب المراحل أعلاه أو تعديله قبل بدء فرع التنفيذ. القرار الأول هو اختيار مزود PostgreSQL والاستضافة للنشر المراقب، وتحديد ما إذا كان الهدف القريب هو إطلاق داخلي مضبوط أم إطلاق إنتاج عام. بعد ذلك يختار المالك أول وحدة ويب للتعميق: **التقارير**، وهي التوصية الافتراضية لأنها أضعف من قدرات الخلفية الحالية، أو **البحث المتقدم** إذا كانت أولوية المستخدمين اليومية أعلى.
