# دليل تشغيل production والمعاينة العامة لمنصة AssetX

**التاريخ:** 2026-08-16
**المستودع:** `Abdulhame709/assetx-enterprise-platform`
**الغرض:** تشغيل نسخة production محلية من web، ربطها بالـ backend المحلي، ثم نشر المنفذ مؤقتاً ليكون قابلاً للفتح من الهاتف.

## النتيجة الحالية

يعمل backend المحلي على المنفذ `3001`، ويعمل web production على المنفذ `3010`. يستخدم web مساراً نسبياً للـ API هو `/api`، بينما يقوم Next.js server-side proxy بتحويل الطلبات إلى `API_PROXY_TARGET`، الافتراضي هو `http://127.0.0.1:3001`.

> الرابط العام المؤقت الذي تم اختباره بنجاح في هذه الجولة هو:
>
> `https://3010-irpjgx3u4two5teoe4qns-0fac8488.us4.manus.computer`

هذا الرابط مرتبط ببيئة sandbox مؤقتة، ولذلك قد يتوقف بعد إيقاف البيئة أو تغيير عملية التعرض العام للمنفذ. لا ينبغي اعتباره رابط production دائم أو رابطاً مناسباً لتوزيعه على مستخدمين نهائيين.

## المتطلبات المحلية

يجب أن يكون PostgreSQL المحلي متاحاً، وأن يكون backend مشغلاً بملف الأسرار الموجود خارج GitHub. لا يتم وضع كلمات المرور أو مفاتيح JWT داخل المستودع.

| الخدمة | المنفذ | فحص الصحة |
|---|---:|---|
| Backend المحلي | `3001` | `curl http://127.0.0.1:3001/health` |
| Backend staging | `3002` | `curl http://127.0.0.1:3002/health` |
| Web dev | `3000` | مناسب للتطوير، وليس رابط الهاتف الموصى به |
| Web production | `3010` | `curl http://127.0.0.1:3010/api/health` |

## تشغيل backend المحلي

يُشغّل backend باستخدام ملف البيئة الخارجي الموجود في `/home/ubuntu/assetx-runtime/backend.local.env`:

```bash
cd /home/ubuntu/assetx-enterprise-platform/backend
set -a
source /home/ubuntu/assetx-runtime/backend.local.env
set +a
npm run build
nohup node dist/main.js > /tmp/assetx-backend-local.log 2>&1 &
```

بعد التشغيل، يجب التحقق من الصحة قبل تشغيل web:

```bash
curl -sS http://127.0.0.1:3001/health
```

الاستجابة المتوقعة تحتوي على `"status":"ok"` و`"database":"ok"`.

## تشغيل web production

بعد نجاح build الخاص بالـ web، يجب تشغيل نسخة production من خلال السكربت المشترك. تم ضبط `npm start` ليغيّر داخلياً إلى مجلد `.next/standalone` قبل تشغيل الخادم، حتى تُقدّم ملفات `/_next/static` (CSS وJavaScript) بصورة صحيحة في المعاينة العامة والهاتف:

```bash
cd /home/ubuntu/assetx-enterprise-platform
npm --prefix web run build
./ops/preview/start-production.sh
```

السكربت يتحقق من وجود ملف بيئة backend، ويفحص صحة backend، ويتأكد من أن المنفذ غير مستخدم، ثم يشغل Next standalone ويتحقق من `/api/health` عبر نفس مسار web. يمكن تغيير المنفذ أو وجهة الـ API دون تعديل الملفات:

```bash
WEB_PORT=3011 \
API_PROXY_TARGET=http://127.0.0.1:3001 \
./ops/preview/start-production.sh
```

إذا كان المنفذ المطلوب مستخدماً، يجب إيقاف العملية القديمة أولاً أو اختيار منفذ جديد. لا يُنصح بقتل كل عمليات Node عشوائياً لأن ذلك قد يوقف backend المحلي وstaging معاً.

## إنشاء رابط عام مؤقت

بعد نجاح فحص `http://127.0.0.1:3010/api/health`، يتم تعريض المنفذ `3010` عبر بيئة التشغيل العامة. الرابط الناتج هو الرابط الذي يُفتح من Android، وليس `127.0.0.1` أو `localhost`.

يجب اختبار الرابط العام بالترتيب الآتي:

| الخطوة | الفحص |
|---:|---|
| 1 | فتح `/login` والتأكد من ظهور نموذج الدخول |
| 2 | تسجيل الدخول بالحساب التجريبي الموثق خارج المستودع |
| 3 | التأكد من الانتقال إلى `/dashboard` |
| 4 | فتح `/reports` مباشرة بعد تسجيل الدخول |
| 5 | فتح `/administration` والتحقق من بقاء الجلسة وظهور المستخدمين والأدوار |
| 6 | إعادة تحميل صفحة محمية والتأكد من عدم العودة إلى spinner دائم أو تسجيل الدخول بلا سبب |

في الاختبار الأخير، نجح مسار الدخول من الرابط العام، وظهرت لوحة التحكم والتقارير والإدارة. أظهر التقارير حالات الفراغ الحقيقية لأن قاعدة البيانات المحلية لا تحتوي على أصول تشغيلية، وأظهرت الإدارة ثلاثة مستخدمين وسبعة أدوار.

## سبب عدم الاعتماد على رابط `3000`

المنفذ `3000` يستخدم خادم dev، وقد ظهرت فيه سابقاً مشكلة hydration وجلسة لا تنتقل من حالة التحميل عند فتح الرابط العام. نسخة production على `3010` تم بناؤها وتشغيلها والتحقق منها، ولذلك هي المسار الموصى به للمعاينة الهاتفية حالياً.

## تشخيص الأعطال

إذا ظهر `ERR_CONNECTION_REFUSED`، يجب فحص العملية والمنفذ:

```bash
ss -ltnp | grep -E ':(3001|3010)\\b' || true
pgrep -af 'node dist/main|next-server|npm start'
```

إذا فتح web لكن أعاد `/api/health` خطأ، يجب التحقق من `API_PROXY_TARGET` ومن صحة backend على `3001`. أما إذا ظهرت صفحة بيضاء أو spinner بحجم الشاشة بعد الدخول، فتحقق أولاً من أن ملفات CSS وJavaScript تعيد HTTP 200، وأن التشغيل يتم من مجلد `.next/standalone` عبر الأمر المضمن في `npm start`. تشغيل `node .next/standalone/server.js` من مجلد `web` مباشرة قد يعيد HTML دون تقديم `/_next/static`، فتظهر SVG والأزرار بحجم غير صحيح. بعد تصحيح المسار، أعد تحميل الصفحة ثم افحص الجلسة إذا استمر spinner.

إذا ظهر `401` بعد تغيير صلاحيات المستخدمين أو الأدوار، فهذا سلوك مقصود عند اختلاف `permission_version`. الحل هو تسجيل الخروج والدخول مرة أخرى أو تنفيذ refresh عبر المسار المعتمد، وليس نسخ token يدوياً بين النطاقات.

## التشغيل من جهاز كمبيوتر لاحقاً

عند تشغيل المشروع على كمبيوتر المستخدم، يجب إنشاء PostgreSQL محلي وتشغيل backend على `3001`، ثم تشغيل web production على منفذ متاح. لا يمكن لرابط عام مؤقت صادر من sandbox أن يستمر بعد انتهاء البيئة؛ للاستخدام الدائم يجب نشر web وbackend في خدمة استضافة أو ربط المشروع ببيئة staging/production ثابتة، مع أسرار محفوظة في متغيرات البيئة لدى منصة الاستضافة.

## قائمة قبول التشغيل

لا تُعتبر المعاينة جاهزة للمراجعة الهاتفية إلا بعد تحقق الشروط التالية:

- backend يعيد health بحالة سليمة وقاعدة البيانات متصلة.
- web production يعيد `/api/health` بحالة `200`.
- صفحة login تفتح من الرابط العام.
- تسجيل الدخول ينقل إلى dashboard ويحفظ الجلسة على نفس origin.
- التقارير والإدارة تفتحان مباشرة بعد تسجيل الدخول.
- لا توجد أسرار في GitHub أو في ملفات المصدر المتتبعة.
- الرابط موصوف بوضوح بأنه مؤقت إذا كان ناتجاً عن بيئة sandbox.
