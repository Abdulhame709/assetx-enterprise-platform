# Preview QA — Working Notes

## 2026-08-14

The temporary preview is running on the independent repository. The first standalone launch served the login page without CSS because `.next/static` was not copied into `.next/standalone`; the preview showed raw Times New Roman markup. A `prepare-standalone.sh` step was added to the web build, the preview was rebuilt, and the login page now renders the centered card, AssetX icon, blue primary button, labels, borders, and page background correctly.

The current public preview URL is temporary and should not be treated as a production endpoint. Backend `/health` returned HTTP 200 before visual inspection.

## Dashboard inspection

The demo login succeeded and `/dashboard` loaded through the public preview. The dashboard has a clear left navigation grouped into Operations, Master Data, and Insights; a breadcrumb; language toggle; user avatar; four KPI cards; and three chart panels. With the empty demo dataset, all KPIs show zero and the chart panels are blank without empty-state guidance. The first visual pass is structurally coherent at the desktop viewport, but the dashboard needs explicit empty states and preferably a seeded preview dataset for meaningful design review.

## Assets and Inventory inspection

The `/assets` page renders a clear toolbar with Export, New Asset, search, Type/Location/Status filters, a disabled-looking Dispose(0) action, and an empty table state. The layout is orderly and the empty state is understandable, although it would be stronger with a direct call-to-action such as “Create your first asset”.

The `/inventory` page renders the page heading, cycle count, and New Cycle action, but the main content card is nearly empty when no cycles exist. It needs a purposeful empty state explaining the field workflow and linking to New Cycle. This is especially important because inventory is the future mobile/offline workflow.

## Movements and Locations inspection

The `/movements` page has a strong operational structure: Pending approvals, All movements, Approved, and Rejected tabs; type/asset/date filters; CSV export; and a meaningful “No pending approvals” empty state that explains which requests will appear.

The `/locations` page loads demo data (`HQ`, type `Room`) and exposes New Root Location, search, add-child, edit, and delete actions. The layout is sparse but clear. The visible label `HQroom` in extracted text appears visually separated as `HQ` and `Room`, suggesting a compact metadata presentation that should be checked for spacing and accessibility semantics.

## Asset Types and Compliance inspection

The `/asset-types` page is visually consistent with Locations: search, New Type, a root item (`IT`), and compact add-subtype/rename actions. It is usable but sparse with the demo dataset.

The `/compliance` page is the strongest desktop screen in this pass. It presents an integrity score of 100, weighted integrity checks, a grid of health checks, and an honest empty state for Controls/Policies/Violations/Remediation stating that the backend APIs are not implemented and no placeholder data is shown. The page is well organized, but the score of 100 on an empty demo dataset should be labeled as “no issues detected in current dataset” rather than implying production health.

## Audit and RTL inspection

The `/audit` page is data-rich and visually useful: it showed 45 events generated by the preview browsing session, with All events/Security tabs, action/entity/date filters, CSV export, event-detail buttons, and pagination. The table is dense but coherent at desktop width.

The Arabic toggle switched the layout to RTL successfully: the sidebar moved to the right, the table order mirrored, dates used Arabic numerals/formatting, and the EN toggle appeared. However, most navigation labels and filter labels remained English, so localization is currently partial rather than a complete Arabic experience. This should be addressed before Arabic-speaking production users rely on the platform.

## RTL and viewport check

The dashboard remained usable in RTL: the sidebar moved right and KPI/chart order mirrored. Browser runtime reported `dir=rtl`, `lang=ar`, viewport `1280x1100`, and no horizontal overflow at that viewport. The public browser capture is scaled differently from the runtime viewport, so a dedicated narrow mobile viewport pass is still required before declaring responsive readiness.
