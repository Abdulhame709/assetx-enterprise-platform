# تقرير جرد الجاهزية قبل التثبيت المحلي

**المشروع:** `assetx-enterprise-platform`
**الفرع الحالي:** `chore/phase1-environment-postgres`
**آخر commit منشور:** `d132499 ui: standardize ERP command toolbar and navigation`
**النطاق:** فحص ما تبقى قبل تثبيت PostgreSQL وتشغيل AssetX محلياً.

## النتيجة التنفيذية

المشروع قابل للانتقال إلى مرحلة التثبيت المحلي من الناحية البرمجية، لكن التثبيت المحلي على **جهاز المستخدم** لم يُنفذ بعد لأن جلسة العمل الحالية ليست متصلة بجهازه. بيئة الفحص الحالية تحتوي على Node.js 22 وpnpm وعميل PostgreSQL 16، كما أن خدمة PostgreSQL تستمع على `127.0.0.1:5432`، لكن لا توجد بيانات اعتماد آمنة مقدمة لهذه الجلسة لإنشاء قاعدة AssetX أو تشغيل migration runner عليها. لذلك لم يتم إنشاء قاعدة، ولم تُطبق migrations، ولم تُنشأ أدوار أو أسرار جديدة.

يجب اعتبار النسخة الحالية **جاهزة تقنياً للتثبيت** وليست مثبتة محلياً عند المستخدم. المسار الصحيح التالي هو ربط كمبيوتر المستخدم أو تنفيذ الأوامر محلياً على جهازه، ثم إنشاء قاعدة فارغة وأدوار منفصلة، وتشغيل runner الرسمي، وseed، واختبار RLS والصحة والمصادقة.

## ما تبقى قبل التشغيل المحلي

أولاً، يجب حسم مكان التنفيذ: إما كمبيوتر المستخدم عبر جلسة سطح مكتب متصلة، أو جهاز تطوير آخر يملك المستخدم صلاحية إدارته. الهاتف وحده لا يستطيع تشغيل PostgreSQL المحلي على كمبيوتر آخر أو الوصول إلى `localhost` الخاص به.

ثانياً، يجب توفير PostgreSQL محلي فارغ وعميل `psql`، ثم إنشاء قاعدة `assetx` وأدوار منفصلة للمهاجر والتطبيق. لا ينبغي استخدام مالك القاعدة لتشغيل HTTP Backend اليومي، ولا ينبغي وضع كلمات المرور داخل المستودع.

ثالثاً، يجب إنشاء ملف أسرار خارج Git يحتوي `DATABASE_URL` وأسرار JWT و`CORS_ORIGIN`، ثم بناء backend وتشغيل `backend` migration CLI الرسمي. سيطبق runner جميع الملفات من `001_init.sql` إلى `012_location_types_catalog.sql` بترتيبها، ويسجلها في `schema_migrations`، ويمكن تشغيله مرة ثانية للتحقق من idempotency.

رابعاً، يجب تشغيل `ops/database/seed-tenant.sh` بعد الترحيلات لإنشاء tenant محلي idempotent وتشغيل seed الصلاحيات داخل سياق `app.tenant_id`. بعدها يُشغل Backend على 3001 وWeb على 3000، ثم تُنفذ health/auth/RLS smoke tests.

خامساً، بعد نجاح التثبيت، يجب فصل التغييرات المصدرية عن وثائق UI audit غير المتتبعة، ومراجعة commit source-only قبل الدفع إلى GitHub. لا ينبغي دفع أسرار أو ملفات env أو قاعدة بيانات محلية.

## عناصر مفتوحة بعد التثبيت وليست عائقاً لتشغيل المحلي

توجد بنود منتجية لاحقة في `todo.md`، أهمها تعميق واجهة التقارير والتشغيلات المتبقية، تطوير التدفق الذكي لجرد المواقع مع المراجعة البشرية، تقوية بعض التوصيات المؤجلة، اختبار نشر PostgreSQL المُدار وأسرار JWT الإنتاجية، توسيع بعض سياسات الاستيراد، ومراجعة بصرية متجاوبة أوسع للهاتف. هذه البنود لا تمنع تشغيل النسخة المحلية الأساسية، لكنها تمنع اعتبارها إصداراً إنتاجياً نهائياً.

توجد أيضاً مراجع توثيقية قديمة تقول إن عدد migrations هو عشرة، بينما المخطط الحالي يحتوي على **12 migration** حتى `012_location_types_catalog.sql`. يلزم تحديث هذه المراجع ضمن commit توثيقي منفصل أو أثناء اعتماد دفعة المصدر، دون تطبيق أي migration إضافية لهذا السبب وحده.

## ترتيب التنفيذ المحلي المقترح

| الترتيب | العمل | معيار النجاح |
|---:|---|---|
| 1 | ربط الكمبيوتر أو فتح جلسة طرفية محلية | الوصول إلى مجلد المشروع على الجهاز المقصود |
| 2 | التحقق من Node وpnpm وPostgreSQL وpsql | الإصدارات متوافقة و`pg_isready` ناجح |
| 3 | إنشاء القاعدة والأدوار المحلية | قاعدة فارغة وأدوار migrator/runtime منفصلة |
| 4 | إنشاء الأسرار خارج Git | الملف بصلاحية مقيدة ولا يظهر في `git status` |
| 5 | بناء Backend وتشغيل migration runner | 12 سجل migration دون خطأ |
| 6 | تشغيل seed tenant والصلاحيات | tenant محلي وصلاحيات idempotent |
| 7 | تشغيل Backend وWeb | `/health` و`/login` يعملان |
| 8 | اختبار auth وRLS والمسار الأساسي | JWT صحيح، tenant isolation ناجح، وإنشاء/قراءة موقع وأصل ناجحان |
| 9 | فحص backup/restore المحلي | dump/restore بعميل متوافق أو توثيق سبب عدم التحقق |
| 10 | اعتماد commit source-only | لا أسرار ولا ملفات قاعدة محلية ولا خلط مع audit docs |

> لا تُطبق migrations من الهاتف أو عبر نسخ SQL عشوائية. المصدر التنفيذي هو `backend/src/bootstrap/migrate.ts` مع `backend/package.json`، أما `PGlite` فهو مسار اختبار/fallback وليس بديلاً عن PostgreSQL المحلي.

## مدخلات لازمة من المستخدم للبدء الفعلي

المطلوب هو **توفير الكمبيوتر أو جلسة سطح مكتب متصلة بالمشروع**. بعد ذلك يمكن استخدام PostgreSQL المحلي الموجود على الجهاز أو تثبيته، مع إنشاء كلمة مرور محلية جديدة لا تُرسل في الدردشة. لا حاجة لإرسال كلمة المرور أو ملف `.env`؛ يكفي أن ينفذ المستخدم القيم محلياً أو يفتح جلسة تسمح بتنفيذها بأمان.
