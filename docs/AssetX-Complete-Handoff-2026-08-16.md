## 1. الخلاصة التنفيذية

**AssetX** منصّة مؤسسية لإدارة دورة حياة الأصول الثابتة، وليست تطبيق جرد منفرداً. تبدأ الدورة من تعريف الأصل والبيانات المرجعية، وتمتد إلى العهدة والموقع والحركات والصيانة والجرد والتقارير والتدقيق والإخراج أو الإتلاف. القيمة الاستراتيجية للمنتج هي تحويل الجرد الميداني إلى عملية رقمية تعمل في بيئة اتصال متقطع، مع حفظ أثر تدقيقي، وعزل المستأجرين، وصلاحيات دقيقة، وإمكانية التوسع إلى EAM ثم SaaS.

المحادثة السابقة بدأت بفحص المستودع الأصلي `Abdulhame709/ASSETS-X`. بعد ذلك اتُخذ قرار واضح بعدم تعديل ذلك المستودع أو دمج التغييرات فيه، وإنشاء نسخة مستقلة خاصة باسم `Abdulhame709/assetx-enterprise-platform`. أُنشئ المستودع المستقل وبدأت فيه معالجة بوابات الإنتاج والأمان، ثم تطور إلى خط أساس متقدم يضم Backend حقيقياً، Web عربية، مسار PostgreSQL، staging وCI، وحدات الأصول والجرد والصيانة والحركات والبيانات الأساسية والاستيراد المنضبط.

في هذه اللحظة، الفرع `main` البعيد عند الالتزام `48faaee`، وفرع العمل المرفوع لهذه الجلسة هو `chore/phase1-environment-postgres` عند الالتزام `f89a85d`. هذا الفرع الأخير أضاف إعداد seed idempotent للصلاحيات وربط الأدوار، ووثّق إعداد PostgreSQL المحلي والتحقق. لم تُدفع أي أسرار إلى GitHub، ولم يتأثر المستودع الأصلي.

المنصّة **ليست إنتاجاً عاماً بعد**. ما تم إنجازه يثبت جاهزية تقنية محلية ومرشحاً مناسباً لبيئة staging مراقبة، لكن الإطلاق الخارجي ما زال يتطلب PostgreSQL مُداراً، أسرار JWT إنتاجية، نطاق Web وBackend، تشغيل الترحيلات والـ seed في بيئة فعلية، اختبار دخان، backup/restore وPITR وقياس RPO/RTO. كما أن تطبيق الهاتف لا ينبغي اعتباره مكتملاً لمجرد وجود مواصفة أو APK داخلي؛ مصدر تطبيق جوال قابل للبناء غير موجود في شجرة المستودع الحالية، ولذلك يجب اعتماد مساره التقني والتحقق منه قبل بدء تطويره.

### 3.1 تعارض التواريخ والوثائق

بعض وثائق `PROJECT_CONTEXT` و`PROJECT_UNDERSTANDING_REPORT` أُعدت عند خط أساس RC1 أقدم مثل `c8a8dce` أو تصف Next.js 14 وReact 18، بينما `web/package.json` الحالي يثبت Next.js 16.3.1 وReact 19.2.8، و`main` الحالي هو `48faaee`. لذلك يجب استخدام **الكود وملفات lock وسجل Git الحالي** لتحديد الحالة التنفيذية، واستخدام الوثائق الأقدم لتاريخ القرارات لا كبديل عن الكود.

وتوجد وثائق rehearsal قديمة تشير إلى سبعة migrations، بينما المجلد الحالي يضم ثمانية ملفات مرقمة من `001_init.sql` إلى `008_maintenance_orders_workflow.sql`. التحقق المحلي الأخير طبّق الثمانية عبر migration runner الرسمي وسجلها في `schema_migrations`. هذه ليست مشكلة في المخطط بقدر ما هي دين توثيقي يجب تحديثه في تقرير مواءمة لاحق دون تعديل وثائق تاريخية بصمت.

## 4. فكرة المنتج ونطاقه

المنتج هو نظام إدارة أصول مؤسسي متعدد المستأجرين. كل أصل يمتلك هوية تقنية UUID وهوية أعمال قابلة للعرض والبحث والطباعة، ويرتبط بفئة ونموذج وحالة وموقع وموظف أو عهدة. تُسجل تغييرات الأصل ضمن دورة حياته، وتُدار الحركات والموافقات، وتُنشأ أوامر الصيانة، وتُنفذ دورات الجرد، ثم تُحل الفروقات وتُراجع وتُغلق مع حفظ السجل التدقيقي.

الجرد هو وحدة ميدانية داخل المنصة. تصميمه المعتمد لا يسمح بتغيير موقع الأصل الرئيسي تلقائياً لمجرد العثور عليه في موقع مختلف. تحفظ اللقطة موقع الأصل المتوقع وقت إنشاء الدورة، ويُحفظ الموقع الفعلي في نتيجة الجرد، ثم يُنشأ اقتراح حركة `transfer` معلقة يحتاج تأكيداً واعتماداً قبل تحديث الأصل الرئيسي. هذا الفصل يحمي البيانات ويمنع تحويل ملاحظة ميدانية إلى تغيير مؤسسي غير قابل للمراجعة.

الأهداف التجارية الموثقة هي تقليل مدة الجرد، خفض الأخطاء، توحيد قاعدة الأصول، بناء تاريخ كامل للأصل، دعم العمل دون اتصال، توفير مؤشرات للإدارة، والاستعداد للتوسع إلى EAM وSaaS. المبادئ غير القابلة للتفاوض هي Offline First وCloud Native وAPI First وSecurity by Design وAudit by Design وMobile First للجرد وModular Architecture وAI Ready وMulti-Tenant Ready.

## 5. المعمارية العامة

```text
Browser / Mobile Client
        │  REST/JSON + Bearer JWT
        ▼
Next.js Web أو تطبيق Field Client
        │
        ▼
NestJS Modular Monolith
  Auth → Tenant/RLS → Permission → Audit
        │
        ├── Application Services / Use Cases
        ├── Domain Entities, Ports, Events
        ├── Repository Implementations
        └── Export, Search, Notifications, SSE
        │
        ├── PGlite محلياً واختبارات
        └── PostgreSQL/Supabase في staging والإنتاج
```

القرار المعماري هو **Modular Monolith أولاً**، وليس Microservices. تطبق الخلفية Clean Architecture عبر `api/` للـ Controllers فقط، و`application/` لحالات الاستخدام، و`core/` للكيانات والعقود والأحداث، و`infrastructure/` لتنفيذ قواعد البيانات والمولدات والمصادقة، و`common/` للحراس والمراقبة وSSE. يمنع وضع SQL أو منطق الأعمال داخل Controller أو الواجهة.

يُستخدم Repository Pattern وحقن الاعتمادات عبر tokens. يفصل EventBus الداخلي بين أحداث الأعمال والتدقيق والإشعارات والتحليلات. يجب أن يبقى تطور API إضافياً داخل الـ Major Version، وأي تغيير Schema يمر قبل تنفيذه عبر ADR وم migration وخطة rollback. لا يجوز إنشاء وحدة كبرى بلا RFC وتصميم واعتماد.

### 5.1 الأمان والعزل

المصادقة تعتمد JWT مع access وrefresh tokens وجلسات مستمرة في `auth_sessions` ومسار logout/revoke وrefresh rotation في كود الخلفية الحالي. يحمي `AuthGuard` التوكن، ويثبت `TenantGuard` سياق المستأجر، ويفرض `PermissionGuard` الصلاحية الدقيقة، ويسجل `AuditInterceptor` طلبات HTTP بينما تسجل خدمات الأعمال أحداث الأعمال مرة واحدة.

يُستخدم `tenant_id` في الجداول التشغيلية مع Row-Level Security. دالة `current_tenant_id()` تقرأ سياق `app.tenant_id`. عند استخدام PostgreSQL، يضع adapter سياق المستأجر داخل transaction قصيرة ويستخدم `AsyncLocalStorage` لتجنب مشاركة Tenant Context بين الطلبات المتزامنة. يجب أن يتصل مسار HTTP بدور غير مالك للجداول حتى تبقى RLS فعالة، بينما تستخدم migrations اتصالاً منفصلاً ذا صلاحيات DDL.

## 6. الخلفية Backend

الخلفية مبنية بـ NestJS 10 وTypeScript. تغطي الوحدات الحالية المصادقة والمستخدمين والمستأجر، الأصول، الفئات والنماذج والحالات والمواقع والموظفين، الجرد، الحركات ودورة الحياة، الصيانة، لوحة المتابعة والتحليلات، التدقيق والامتثال، الإشعارات وSSE، التصدير، البحث المتقدم والبحث المحفوظ، التقارير والقوالب والتقارير المجدولة، قواعد الأعمال وسير العمل، وفحص السلامة.

مسارات API الرئيسية تشمل `auth` و`tenant/current` و`assets` و`inventory` و`movements` و`lifecycle` و`maintenance` و`dashboard` و`analytics` و`compliance` و`audit` و`notifications` و`exports` و`search` و`saved-searches` و`employees` و`locations` و`categories` و`models` و`statuses` و`users` و`health`.

بوابة المصادقة الحالية تشمل `POST /auth/register` و`POST /auth/login` و`POST /auth/logout` و`POST /auth/refresh` و`POST /auth/reset-password`. يجب عدم تغيير هذه العقود كسرّياً. تدفق تسجيل الدخول يستخدم `authenticate_user`/lookup الآمن قبل بناء الجلسة، ويجب إعادة اختبار ذلك على PostgreSQL المُدار لأن RLS تحمي `users`.

## 7. قاعدة البيانات

المصدر التنفيذي هو مجلد `db/migrations/`، وليس الوصف التاريخي وحده. المخطط يضم 24 جدولاً موثقاً، وستة أنواع Enum أساسية، وعلاقات Foreign Key وفهارس وقيوداً وTriggers، وView محسوبة لنتيجة الجرد. المواقع تستخدم مساراً هرمياً متوافقاً مع LTREE عند توفر الامتداد، مع fallback نصي متوافق.

الجداول الأساسية تشمل `tenants` و`organizations` و`users` و`employees` و`roles` و`permissions` و`role_permissions` و`user_roles` و`user_permissions`، ثم `asset_categories` و`asset_models` و`statuses` و`locations` و`assets`، وجداول `asset_movements` و`maintenance_orders` و`inventory_cycles` و`inventory_team` و`inventory_records`، إضافة إلى `audit_events` و`notification_templates` و`notifications` و`settings` و`auth_sessions` و`password_reset_tokens` و`saved_searches` وكائنات التقارير والتصدير بحسب المخطط الحالي.

الترحيلات الحالية هي:

| الترحيل | الغرض |
|---|---|
| `001_init.sql` | المخطط الأساسي، RLS، الفهارس، الدوال، العرض المحسوب |
| `002_movement_lifecycle.sql` | دورة حياة الحركة وحالات الاعتماد |
| `003_saved_searches.sql` | البحث المحفوظ وRLS الخاص به |
| `004_password_reset_tokens.sql` | رموز استعادة كلمة المرور |
| `005_authenticate_user_function.sql` | دالة lookup آمنة للمصادقة |
| `006_auth_sessions.sql` | الجلسات المستمرة والـ refresh |
| `007_runtime_grants.sql` | امتيازات حساب التشغيل غير المالك |
| `008_maintenance_orders_workflow.sql` | أوامر الصيانة وسير حالات العمل |

أضيف في فرع المرحلة الأولى `db/seed/002_permissions.sql`. السبب أن `db-init.ts` المحلي كان يستدعي `seedPermissions`، بينما تهيئة PostgreSQL الخارجية تحتاج seed صريحاً لكتالوج الصلاحيات وربط الأدوار. الملف الجديد idempotent ويتطلب ضبط `app.tenant_id`، ويجب تشغيله بعد `db/seed/001_seed.sql` ضمن الجلسة نفسها أو ضمن سياق مستأجر صحيح.

### 7.1 تسلسل تهيئة staging والإنتاج

يُنشأ دور `authenticated` وحساب runtime بواسطة مسؤول قاعدة البيانات مرة واحدة. لا يُمنح Backend صلاحية `CREATEROLE`، ولا يُستخدم مالك القاعدة في كل طلب HTTP. بعد ذلك يطبق migration job مستقل ملفات الترحيل، ثم يُنشأ المستأجر الأول وتُضبط قيمة `app.tenant_id`، ثم تُشغل seed البيانات الأساسية وseed الصلاحيات. لا ينبغي تشغيل `RUN_MIGRATIONS=true` داخل خدمة Backend الإنتاجية؛ الترحيل job محمي ومسبق بــ backup وخطة rollback.

## 8. بيئات التشغيل

### 8.1 التطوير المحلي

المتطلبات الحالية Node.js 20+، والبيئة المفحوصة استخدمت Node 22 وnpm 10. يعمل Backend على المنفذ 3001، وWeb على 3000. إذا لم يوجد `DATABASE_URL` يستخدم Backend PGlite المدمج ويطبق bootstrap محلياً، وينشئ tenant `demo` وحساب `admin` وبيانات مرجعية. يمكن تشغيل dataset العرض اختيارياً عبر `ASSETX_SEED_DEMO=1 npm start`.

إذا وُجد `DATABASE_URL` ينتقل Backend إلى `PostgresDatabase`. في إعداد المرحلة الأولى أُثبت PostgreSQL 16 محلياً على `127.0.0.1:5432`، وأُنشئت قاعدة `assetx`، وفُصل حساب `assetx_migrator` عن `assetx_app`، وحُفظت الأسرار خارج المستودع في `/home/ubuntu/assetx-runtime/`. هذه بيئة تحقق مؤقتة داخل Sandbox وليست خدمة مستمرة أو إنتاجية.

تشغل الواجهة حالياً عبر same-origin proxy:

```text
NEXT_PUBLIC_API_URL=/api
NEXT_PUBLIC_AUTH_MODE=real
API_PROXY_TARGET=http://127.0.0.1:3001
```

هذا يمنع أن يحاول متصفح الهاتف استخدام `localhost` الخاص بجهاز المستخدم. في الإنتاج يجب ضبط `API_PROXY_TARGET` إلى خدمة Backend الداخلية عند البناء أو النشر، وعدم إدخال أسرار Backend ضمن `NEXT_PUBLIC_*`.

### 8.2 Staging عبر Docker Compose

`docker-compose.staging.yml` يعرّف خدمتي Backend وWeb. Backend يحتاج `CORS_ORIGIN` و`DATABASE_URL` و`JWT_ACCESS_SECRET` و`JWT_REFRESH_SECRET` ويشغل health check على `/health`. Web يبنى مع `API_PROXY_TARGET=http://backend:3001` ويعرض المنفذ 3000. الترحيلات تُنفذ كـ job منفصل، ثم تشغل الخدمات بعد نجاحها.

### 8.3 الإنتاج

الإنتاج يحتاج PostgreSQL مُداراً عبر TLS، نطاق Web وBackend، `CORS_ORIGIN` مطابقاً حرفياً لنطاق الواجهة، أسرار JWT طويلة وفريدة عبر secret manager، TLS وheaders/CSP، logging منقحاً، ومراقبة للهوية وقاعدة البيانات. يلزم تنفيذ backup/restore وPITR وقياس RPO/RTO قبل إعلان الجاهزية. لم يتم تنفيذ هذه الخطوة خارجياً لأن بيانات الموفر والنطاق والأسرار غير متوفرة في الجلسة الحالية.

## 9. الواجهة Web

الواجهة الحالية مبنية فعلياً على Next.js App Router وReact 19 وTailwind وTypeScript، مع تصميم مؤسسي عربي قائم على tokens ومكونات UI مشتركة. طبقات البيانات تستخدم `lib/api/client.ts` ثم `features/*/api.ts` وMappers قبل الصفحات، فلا ينبغي تمرير DTO خام إلى الواجهة.

المسارات الظاهرة للمستخدم تشمل لوحة المتابعة والبحث والإشعارات والأصول وتفاصيل الأصل والجرد وتفاصيل دورة الجرد والصيانة والحركات والاستيراد والبيانات الأساسية للمواقع وأنواع الأصول والحالات والموظفين، ثم التقارير والتحليلات والامتثال والتدقيق، وأخيراً الإدارة والإعدادات. بناء الإنتاج الحالي يولد 23 مساراً، منها المسارات النظامية والتفاصيل الديناميكية.

### 9.1 ما تم إنجازه في Web

تم بناء App Shell وSidebar وTopbar وRTL والتعريب وتدفقات الأصول وتفاصيل الأصل والجرد والصيانة والحركات والبيانات الأساسية وحالات الأصول. عولجت أزرار الحفظ والتعديل والتعديل الجماعي والنسخ والتراجع والحذف الناعم والاستيراد وفق الصلاحيات، وأضيف استيراد Excel محكوم للأصول ثم توسع إلى المواقع وأنواع الأصول وحالات الأصول والموظفين مع قالب ومعاينة وتحقق وسجل تدقيق.

أعيد تصميم Workspace الأصول ليضم البحث الذكي وقائمة تشغيلية ولوحة تفاصيل. أضيفت رسائل رفض عربية عندما يمنع تعطيل نوع أو حالة بسبب ارتباط أصل نشط، مع منع الحذف المادي. عُربت صفحات الموظفين والجرد والصيانة والحركات، وأضيفت صفحة حالات الأصول، وأغلقت عيوب Preview القديمة الخاصة بالـ chunks والبناء.

### 9.2 الفجوات الحالية في Web

صفحة التقارير الحالية تثبت وجود مؤشرين وزر CSV للأصول، لكنها لا تعرض بعد Report Builder كاملاً أو القوالب أو اختيار الموارد والفلاتر أو PDF/XLSX أو الجدولة. لذلك تكون التقارير أول مرشح لتعميق تجربة الويب بعد إغلاق بيئة staging.

صفحة البحث الحالية asset-only: حقل نصي يستخدم `useAssetList` ويعرض روابط للأصول. قدرات Backend للبحث المتقدم والبحث المحفوظ أوسع من هذا العرض، ولذلك يجب إضافة فلاتر الموقع والنوع والحالة والموظف وحفظ البحث واستعادته ضمن صلاحيات المستأجر.

صفحة الإدارة الحالية تعرض ملخص المستخدم والمستأجر وعدد الصلاحيات، ولا توفر بعد إدارة كاملة للمستخدمين والأدوار والصلاحيات والمستأجرين. صفحة الإعدادات الحالية تركز على اللغة، وصفحة الإشعارات أساسية وتحتاج إثراء SSE والفلاتر والتفضيلات عند اعتمادها. يجب ألا تُعامل هذه المسارات كـ Done لمجرد وجود route.

## 10. تطبيق الهاتف والربط مع المنصّة

المواصفة المعتمدة `Mobile/Mobile_Technical_Specification.md` تصف تطبيق Field Inventory متعدد المنصات مبنياً أساساً بـ Flutter، مع SQLite محلي، Repository Pattern، Sync Queue، Incremental Sync، Conflict Resolver، QR/Barcode، Camera، GPS، FCM، Secure Storage، Device Management، وواجهة عربية أولاً. هذه مواصفة تصميمية approved baseline وليست دليلاً على وجود مصدر التطبيق في المستودع.

فحص شجرة المستودع الحالية لم يجد `pubspec.yaml` أو `pubspec.lock` أو `app.json` أو `eas.json` أو مصدر Android/Flutter. توجد إشارة في وثيقة Production Readiness إلى APK داخلي من Expo، لكن وجود APK لا يثبت وجود مصدر قابل لإعادة البناء أو أن قرار Flutter الموثق طُبق فعلاً. لذلك يجب في المرحلة القادمة تحديد مصدر الـ APK، أو إعادة بناء التطبيق من المواصفة، أو اعتماد React Native/Expo بــ ADR منفصل إذا كان ذلك هو القرار العملي. لا يجب افتراض أن الموبايل مكتمل.

### 10.1 العقد الوظيفي الصحيح للجوال

يبدأ المستخدم بدورة جرد ثم يختار موقع عمل فعلي. تنزل إلى الجهاز لقطة تحتوي `record_id` و`asset_id` و`asset_code` و`expected_location_id` و`expected_location_name` و`expected_location_path` و`actual_location_id` و`expected_quantity` و`actual_quantity` و`result` و`is_verified` و`updated_at`. كل عد أو اقتراح نقل يحفظ محلياً أولاً، ثم يدخل Outbox دائم بمفتاح idempotency قبل أي اتصال.

عند الضغط على «موجود في هذا الموقع» تصبح الكمية الفعلية مساوية للمتوقعة ويُحفظ الموقع المتوقع. يبقى الأصل غير المؤشر عليه ضمن `لم يُجرد`. عند مسح أصل في موقع مختلف يعرض التطبيق المتوقع والمرصود، ولا ينفذ النقل تلقائياً. عند تأكيد المستخدم يرسل `actual_location_id` وينشئ اقتراح حركة `transfer` معلقة؛ لا يتغير الموقع الرئيسي إلا بعد اعتماد الحركة من Web وبأثر تدقيقي.

## 12. ما بقي فعلياً

### 12.1 بوابة الإنتاج

أولوية الإغلاق الأولى هي تكرار rehearsal على PostgreSQL/Supabase فعلي، إنشاء الأدوار بصلاحيات أقل، تطبيق migrations كـ job، seed tenant والصلاحيات، تشغيل Backend/Web عبر Docker أو منصة الاستضافة، وضبط TLS وCORS والأسرار. بعد ذلك تنفذ اختبارات دخان مستقلة للحساب، الأصول، الحالات، الصيانة، الجرد، الاستيراد، التدقيق، العزل والنسخ والاستعادة. ما لم يتم ذلك، تبقى المنصّة مرشح staging لا production.

### 12.2 توحيد الوثائق

يجب إنشاء مواءمة رسمية بين الكود الحالي والوثائق القديمة. التعارضات المعلنة هي تعدد تعريفات Roadmap، اختلاف عدد الوحدات، UUID مقابل Business Code، اختلاف صلاحيات Print، نتيجة الجرد computed مقابل stored، semantics الحذف الناعم، وإعادة استخدام أرقام ADR. ديون D1 وD2 وD3 محفوظة عمداً ولا تُحل تلقائياً. المطلوب سجل قرار جديد يحدد ما إذا كانت ستبقى Pending أو تُعتمد رسمياً.

### 12.3 تعميق الويب

الأولوية بعد staging هي تقرير مؤسسي قابل للفلاتر والتصدير والمعاينة، ثم البحث المتقدم والبحث المحفوظ، ثم إدارة المستخدمين والأدوار والصلاحيات، ثم إثراء الإشعارات والإعدادات والمرفقات. كل وحدة يجب أن تشمل صلاحيات، loading/empty/error، تعريباً حقيقياً، اختبارات، وبناء إنتاج ومراجعة هاتفية.

### 12.4 الموبايل

المطلوب أولاً قرار مصدر وتقنية. إذا اعتمد Flutter، تنشأ حزمة mobile مستقلة وفق المواصفة. إذا اعتمد React Native/Expo بسبب APK الموجود، يجب إنشاء ADR يفسر تغيير القرار واسترداد source قابل للبناء. بعد ذلك تبنى طبقات auth وSQLite وoutbox/inbox والمزامنة والتعارض والتشفير وQR والصور/GPS وإدارة الجهاز، ثم اختبارات جهاز حقيقي في وضع الطيران وإعادة التشغيل والشبكة المتقطعة.

### 12.5 التقوية والتوسع

تبقى async export وBullMQ/Redis وS3 وemail exports وscheduled exports وaudit retention وread models وpartitioning وload testing بنوداً مؤجلة في Technical Debt Register. لا تُفتح قبل تحقق محفز تشغيلي أو اعتماد صريح، ولا تُضاف إلى النطاق لمجرد وجودها في الوثائق.

## 13. خطة الاستمرار الدقيقة

### المرحلة 0 — اعتماد خط الحقيقة

يعتمد الفريق هذه الوثيقة باعتبارها نقطة التسليم، ويثبت فرع العمل من `f89a85d` أو من `main` بعد دمج التوثيق والـ seed. يُحدّث سجل الحالة ليشير إلى `48faaee` و`f89a85d`، ويُسجل أن بعض الوثائق التاريخية أقدم من الكود الحالي. لا يبدأ تغيير Schema أو تطبيق موبايل قبل اعتماد النطاق.

**بوابة الخروج:** حالة Git واضحة، لا أسرار متعقبة، مصفوفة tests قابلة لإعادة التشغيل، ووثيقة قرار تحدد أي الوثائق تعتبر تاريخية وأيها مصدر تشغيل.

### المرحلة 1 — Staging حقيقي

يختار مالك المشروع مزود PostgreSQL والاستضافة، ثم يوفر `DATABASE_URL` عبر TLS، نطاق Web، نطاق Backend أو proxy، `CORS_ORIGIN`، `JWT_ACCESS_SECRET`، `JWT_REFRESH_SECRET`، وأدوار database المنفصلة. تنشأ قاعدة staging فارغة، يُنشأ `authenticated` وruntime role، تُطبق migrations الثمانية، يُنشأ tenant، ويُشغل seed `001` ثم `002_permissions` في سياق tenant.

بعد الإقلاع ينفذ smoke test للحساب والتوكن والـ refresh/logout، ثم الأصول والبيانات الأساسية والصيانة والحركات والجرد والاستيراد والتدقيق والعزل. يُختبر backup/restore إلى قاعدة مؤقتة، ثم PITR وRPO/RTO والتنبيهات. لا يُعلن الإنتاج إلا بعد نجاح هذه البوابة.

### المرحلة 2 — إكمال Web ذات الأولوية

تُبنى التقارير أولاً، مع اختيار الموارد والفترة والفلاتر ومعاينة وCSV/XLSX/PDF وقوالب تحفظ بالصلاحيات. بعدها يضاف البحث العام عبر الأصول والحركات والتدقيق والمواقع مع saved searches. ثم تتحول الإدارة من ملخص جلسة إلى إدارة مستخدمين وأدوار وصلاحيات ومستأجر، مع audit وpermission versioning.

**بوابة الخروج:** كل صفحة تملك عقد API واختباراً وتدفق فشل وحالة فراغ وتعريباً ومراجعة هاتفية.

### المرحلة 3 — تثبيت عقد الموبايل

يعتمد قرار Flutter أو React Native/Expo عبر ADR. توحد أسماء الحقول ومعرفات UUID والـ timestamps وidempotency keys وcursor sync وACK/error codes. يراجع الفريق `Field-Inventory-Location-Workflow-Spec.md` ويحوّله إلى contract tests قبل كتابة واجهة الجهاز.

### المرحلة 4 — تطبيق الجوال والمزامنة

ينفذ التطبيق auth وsecure token storage، تنزيل الدورات، local SQLite، location work session، quick match، QR، uncounted queue، undo وauto-advance، outbox دائم، incremental sync، retries، conflict dashboard، ثم الصور/GPS/device management عند اعتمادها. لا يُقبل التطبيق بإنجاز شاشات فقط؛ معيار النجاح هو جرد كامل دون شبكة، إعادة تشغيل، تكرار طلب، تعارض، واستئناف دون فقد.

### المرحلة 5 — التقوية والإطلاق

بعد إثبات الاستخدام الفعلي، يفتح الفريق async exports وqueue/workers وobject storage وaudit retention وread models وفق ADRs مستقلة. تجرى load/performance tests، SBOM وفحص أسرار واعتماديات، ثم UAT، release train، semantic version، rollback runbook، مراقبة مركزية، وإطلاق Android/iOS وفق المصدر القابل لإعادة البناء.

## 15. قواعد التعاون المستمرة

يعمل الفريق بالعربية في الواجهة والتوثيق قدر الإمكان، مع دعم الإنجليزية عند الحاجة. يجب أن تكون العربية حقيقية في labels وvalidation وempty/error states، لا مجرد `dir="rtl"`. كل زر يجب أن يملك سلوكاً حقيقياً وصلاحية واضحة، أو يصرح بأنه غير متاح؛ لا تُترك أزرار شكلية.

بعد كل تحديث مهم تُشغل الاختبارات الآلية وبناء الإنتاج، وتُراجع الواجهة على الهاتف، وتُفحص الرحلة من Browser إلى API إلى Database. لا يستخدم الفريق `npm audit fix --force`. لا تُضاف migrations أو وحدات كبرى دون ADR/RFC/اختبارات/توثيق وخطة rollback. لا ينتقل الفريق من مرحلة إلى أخرى قبل اجتياز بوابة الخروج الحالية.
