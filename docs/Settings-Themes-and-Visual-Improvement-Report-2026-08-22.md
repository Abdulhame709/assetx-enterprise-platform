# تقرير إعدادات أنواع المواقع والثيمات والتحسينات البصرية

**المشروع:** `assetx-enterprise-platform`
**التاريخ:** 22 أغسطس 2026
**النطاق:** تنفيذ الميزات المؤكدة فقط من تشخيص Visual Design System، مع الحفاظ على Clean Architecture وRBAC/RLS والعزل حسب المؤسسة والتدقيق.

## الخلاصة التنفيذية

أصبح إعداد أنواع المواقع موجوداً في صفحة **الإعدادات ← أنواع المواقع**، بدلاً من بقائه قائمة ثابتة داخل نموذج المواقع. يمكن للمستخدم المخول إنشاء نوع جديد برمز داخلي واسم عربي واسم إنجليزي اختياري وأيقونة وترتيب، وتعديل الاسم والأيقونة والترتيب، وتعطيل النوع أو إعادة تفعيله. لا يمكن تغيير الرمز بعد الإنشاء لأن المواقع تخزنه كمرجع تشغيلي؛ كما لا يمكن تعطيل نوع مستخدم بواسطة مواقع نشطة.

تم تحويل عقد `location_type` إلى قيمة نصية مربوطة بـcatalog خاص بالمؤسسة عبر migration `012_location_types_catalog.sql`. بقيت أكواد الأنواع القياسية الخمسة متوافقة مع البيانات الحالية: `building`, `room`, `warehouse`, `workshop`, و`outdoor`. نموذج الموقع والشجرة يعرضان الاسم والأيقونة من catalog، ولذلك ستظهر الأنواع المخصصة الجديدة دون تعديل واجهة المواقع مرة أخرى.

أضيفت أربعة ثيمات قابلة للتبديل: **أزرق مؤسسي، منتصف الليل، زمردي، وجرافيت**. التبديل فوري ويحفظ الاختيار في المتصفح فقط عبر `assetx.theme.v1`؛ لم يُفرض حفظ تفضيل العرض على المؤسسة أو المستخدم في قاعدة البيانات لأن ذلك ليس ضرورياً للميزة الحالية ولا ينبغي أن يخلط تفضيلات العرض ببيانات الأعمال.

## أين أضبط أنواع المواقع؟

افتح **الإعدادات** من القائمة الجانبية، ثم قسم **أنواع المواقع**. تظهر فيه الأنواع الحالية مع حالتها ورمزها وترتيبها، وتوجد أزرار icon-only للتعديل والتفعيل أو التعطيل. زر **نوع موقع جديد** يفتح نموذجاً يحتوي على الحقول التالية:

| الحقل | الغرض | القاعدة |
|---|---|---|
| الرمز | المرجع الداخلي الذي تخزنه المواقع | أحرف إنجليزية صغيرة وأرقام و`-` أو `_`، ولا يتغير بعد الإنشاء |
| الاسم العربي | الاسم الظاهر في الواجهة العربية | مطلوب، من حرفين إلى 120 حرفاً |
| الاسم الإنجليزي | الاسم الظاهر عند اختيار English | اختياري، من حرفين إلى 120 حرفاً عند تعبئته |
| الأيقونة | الرمز البصري في نموذج الموقع وشجرة المواقع | من مجموعة أيقونات معروفة وآمنة |
| الترتيب | ترتيب الظهور في القوائم | عدد صحيح من 0 إلى 9999 |

يجب استخدام أسماء تشغيلية واضحة مثل **مجمع، موقع ميداني، مركز خدمة، مختبر، أو موقف مركبات** بحسب طبيعة المؤسسة. لا أنصح بإنشاء نوع لكل مبنى أو فرع؛ النوع يصف طبيعة الموقع، بينما اسم الموقع نفسه يصف المكان الفعلي.

## ما تم تنفيذه

| المجال | التنفيذ | الضمانات |
|---|---|---|
| catalog أنواع المواقع | جدول `location_types` مستقل لكل tenant | RLS، مفتاح فريد داخل المؤسسة، تحقق من الرمز والاسم |
| ربط المواقع | `locations.location_type` أصبح code نصياً مع FK مركب `(tenant_id, code)` | لا يمكن لموقع استخدام نوع من مؤسسة أخرى |
| النموذج والشجرة | تحميل الأنواع من `/location-types` وعرض الاسم/الأيقونة من الخادم | لا توجد قائمة enum ثابتة في الواجهة |
| التعطيل | soft deactivate فقط | يمنع التعطيل إذا كان النوع مستخدماً في مواقع نشطة |
| الصلاحيات | `location_type.view/create/update/delete` و`settings.view/update` | صلاحيات مستقلة؛ أدوار عرض المواقع تحصل على صلاحية قراءة النوع فقط |
| التدقيق | حدث `LOCATION_TYPE_DEACTIVATED` بالإضافة إلى تدقيق الطلبات العام | لا يوجد حذف فعلي للنوع أو للمواقع |
| الثيمات | `ThemeProvider` وtokens في `globals.css` | محفوظة محلياً في المتصفح، ولا تمس منطق الأعمال |
| تحسينات UI | إزالة زر Columns غير الموصول، focus trap في Modal، keyboard navigation في SearchableSelect، وتعريب aria-label في Toast | تحسين accessibility دون حذف إجراءات أو تغيير API |

## ما لم يتم نقله عمداً

لم تتم إضافة الحقول القديمة مثل مسؤول الموقع أو بيانات الاتصال أو الوصف إلى نوع الموقع، لأنها ليست مطلوبة لتشغيل catalog الحالي ولا يوجد لها عقد أعمال حديث أو استخدام في الأصول والتقارير. كذلك لم تتم إعادة numeric gap-reuse codes أو منطق WPF أو الحذف الفعلي. هذه قرارات حماية من التكدس والتعارض، وليست نقصاً في التنفيذ.

لم تتم إضافة نقل الموقع بين آباء من واجهة المواقع في هذه المرحلة. مراجعة legacy أثبتت أن النقل يحتاج contract مستقل وإعادة حساب descendants، بينما عقد المواقع الحالي لا يطلب هذه الميزة صراحة. أما نقل **أنواع الأصول** الهرمية فهو جزء منفذ سابقاً مع منع الدورات وإعادة بناء المسارات.

## اقتراحات التحسين البصري التالية

### أولوية أولى: توحيد كثافة صفحات البيانات

ينبغي اعتماد قاعدة ثابتة لكل صفحة master-data: `PageHeader`، ثم `CommandToolbar` موحد، ثم شريط بحث وفلاتر، ثم بطاقة بيانات واحدة. على الشاشات الصغيرة يتحول toolbar إلى صف قابل للتمرير أفقياً أو قائمة أوامر، بدلاً من ضغط جميع الأيقونات في مساحة ضيقة. يجب أن تبقى labels في tooltip وaria-label، مع عدم إخفاء الإجراء الوحيد خلف hover فقط.

### أولوية ثانية: نظام أيقونات دلالي مركزي

يجب أن تبقى الأيقونات مرتبطة بالمعنى، لا بالزخرفة. أقترح الالتزام بحجمين فقط داخل الإجراءات: حاوية `32px` للإجراءات الأساسية وحاوية `28px` للإجراءات الصفية، مع `stroke-width` ثابت، وحالات موحدة للـhover/focus/disabled. الأنواع والمواقع تستخدم registry مركزي مثل الذي أضيف لأنواع المواقع، حتى لا تظهر أيقونات مختلفة لنفس المعنى بين صفحة وشجرة وmodal.

### أولوية ثالثة: تحسين الجداول على الهاتف

الجداول العريضة ينبغي أن تستخدم أعمدة أولوية مع drawer أو preview للصف الكامل، مع إبقاء الاسم والحالة والإجراء الأساسي مرئية. لا ينبغي تحويل كل الأعمدة إلى بطاقات منفصلة لأن ذلك يكرر المعلومات ويضعف المقارنة. الأفضل أن يبقى الجدول مصدر الحقيقة وأن يكون العرض الجانبي طبقة تفصيل.

### أولوية رابعة: توحيد حالات النظام

كل صفحة تحتاج حالات loading وempty وerror وsuccess بصرياً موحداً، مع رسالة عربية واضحة وإجراء إصلاح مباشر مثل إعادة المحاولة أو مسح الفلتر. يجب أن تظهر الحالة غير النشطة كـBadge دلالي، وألا يكون اللون وحده هو الوسيلة الوحيدة لفهم الحالة.

### أولوية خامسة: فصل theme tokens عن page styles

الثيمات الحالية مبنية على semantic tokens، ولذلك يمكن إضافة ثيم مؤسسي لاحقاً دون إعادة تلوين كل صفحة. إذا تطلب المنتج لاحقاً مشاركة الثيم بين مستخدمي المؤسسة، يمكن نقل `theme_id` إلى settings أو user preferences، لكن بعد تحديد هل التفضيل شخصي أم مؤسسي. لا ينبغي تخزين مجموعة CSS خام أو ألوان يرسلها المستخدم مباشرة إلى الواجهة.

## حدود النشر والتحقق

تمت إضافة migration ولم تُطبّق على PostgreSQL خارجي أو قاعدة محلية مستقلة. أُعيد تشغيلها في PGlite ضمن test harness، ونجحت اختبارات catalog والعزل. نتائج التحقق الحالية هي:

| اختبارات backend unit | 26/26 عبر 4 suites |
| اختبارات web | 74/74 عبر 14 ملفاً |

تغييرات المصدر والوثائق ما زالت في working tree ولم يتم إنشاء commit أو push في هذه المرحلة. كما لم تُخلط حزمة UI audit السابقة أو تُحذف؛ بقيت ملفاتها غير المتتبعة كما طلبت سابقاً.
