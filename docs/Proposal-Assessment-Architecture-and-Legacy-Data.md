# تقييم مقترحات المعمارية والبيانات القديمة — AssetX

**الحالة:** تقييم وقرار فقط؛ لا يتضمن هذا التقرير تنفيذ ميزة أو ترحيلاً أو تغييراً في المخطط.  
**الغرض:** مقارنة المقترحات الواردة في الملفات المرفقة مع منصة AssetX الحالية، ثم التوصية بما يضيف قيمة مؤسسية من دون تضخيم نطاق المنتج أو تقليل أمانه.

## الخلاصة التنفيذية

المقترحات المرفقة قوية من ناحية الرؤية، لكنها ليست نقطة بداية جديدة للمشروع. وثائق AssetX الحالية تبنت بالفعل عدداً من القرارات الصحيحة: **Monolith معياري أولاً، UUID تقني مع رمز عمل بشري، جاهزية تعدد المستأجرين، مسار مادي للمواقع، جرد Offline-first، وADR-001 حتى ADR-007**. لذلك لا أوصي بإعادة كتابة الوثيقة الأساسية إلى «الإصدار 5.0» أو نسخ مخطط SQL Server القديم؛ بل أوصي بتعزيز ما هو موجود، وحل فجوات التوثيق والتنفيذ ذات الأولوية بقرارات قصيرة قابلة للمراجعة.

> القرار الحاكم: يحتفظ AssetX بالمنطق التشغيلي المفيد من النظام السابق، لكنه لا يرث قيود SQL Server، مفاتيح Identity، الجداول أحادية الجهة، أو العمليات الإدارية الخطرة من الواجهة.

## الوضع القائم الذي تأكدت مراجعته

| المجال | الوضع في AssetX الحالية | التقييم |
|---|---|---|
| المعمارية | وثيقة المعمارية تعتمد Modular Monolith وتوضح متى يمكن الانتقال لاحقاً إلى خدمات مستقلة. | قرار صحيح؛ لا تغيير تقني الآن. |
| الهوية والبيانات | وثائق قاعدة البيانات تعتمد UUID كمفتاح تقني و`tenant_id` وعناصر تدقيق معيارية، بينما تبقى أكواد الأصول معرفات بشرية. | قرار صحيح ومتوافق مع المقترح. |
| تعدد المستأجرين | Backend يمرر نطاق الجهة في طبقة الخدمة والاستعلامات؛ الوثائق تحدد RLS لـPostgreSQL كطبقة عزل إضافية. | جيد، لكنه يحتاج إثبات RLS في بيئة PostgreSQL المدارة قبل الإنتاج. |
| المواقع الهرمية | القرار الموثق هو Materialized Path مع LTREE وGIN؛ التنفيذ الحالي يستخدم أيضاً `parent_id` ومسارات عرض. | يبقى القرار صحيحاً، لكن يحتاج ADR تنفيذي قبل تفعيل LTREE فعلياً. |
| الجرد والميدان | توجد دورة جرد وسجل ونتائج محسوبة ومساعد موقع L1؛ التطبيق الجوال مصمم offline-first. | الأساس موجود؛ مراقبة الأجهزة والتعارضات ليست مكتملة في لوحة الإدارة. |
| التدقيق والصلاحيات | توجد RBAC وتدقيق وحذف ناعم وحماية للأصول المرتبطة. | أساس مناسب لتوسيع الحوكمة، وليس سبباً لبناء Approval Engine عام الآن. |

## قرار كل مقترح

| المقترح | المطابقة الحالية | القرار | التوقيت الموصى به | سبب القرار |
|---|---|---|---|---|
| فصل الوثيقة الكبيرة إلى منظومة وثائق | توجد وثائق مستقلة للمعمارية وقاعدة البيانات وAPI، لكن يوجد تكرار وDecision Log يسجل تعارضات معلقة. | **اعتماد بتحسين محدود** | الآن، توثيق فقط | أنشئ فهرساً مرجعياً وChange Log وADR قابلة للعثور، لا مشروع «إعادة كتابة» يوقف التطوير. |
| تقليل MVP | بعض وحدات Enterprise موجودة بالفعل في المنصة. | **اعتماد كسياسة إصدار** | الآن | لا نحذف الوحدات المنفذة، لكن نحدد بوابات قبول للنسخة الأساسية: الأصول، البيانات الأساسية، الجرد، RBAC، التدقيق والتقارير الأساسية. |
| Modular Monolith قبل Microservices | موثق ومطبق في NestJS. | **موجود — لا تغيير** | مستمر | أي فصل خدمات الآن يزيد التعقيد التشغيلي من دون دليل حمل أو فرق مستقلة. |
| Domain-Driven Design وBounded Contexts | الوحدات الحالية تفصل الأصول والجرد والصيانة والتدقيق والمصادقة. | **تحسين توثيقي** | قريب | تسمية السياقات وتحديد ملكية البيانات مفيد، لكن لا يلزم إعادة ترتيب جذرية للكود. |
| NFRs | لا يوجد حتى الآن ملف قبول تشغيلي موحد قابل للقياس لكل وحدة. | **اعتماد عالي القيمة** | قبل النشر العام | يضيف حدوداً موضوعية للأداء والتوافر والاستعادة والحماية، بدلاً من عبارات عامة عن الجاهزية. |
| Event-driven architecture | يوجد تدقيق وإشعارات، لكن لا حاجة مثبتة إلى Event Broker خارجي. | **تأجيل البنية الخارجية** | بعد استقرار V2 | ابدأ بواجهات Domain Events داخل الـMonolith؛ لا تضف Kafka/RabbitMQ الآن. |
| Multi-tenant SaaS | مبدأ `tenant_id` وRLS موثق؛ لا توجد حاجة إلى Billing في MVP. | **اعتماد مع إغلاق فجوة** | قبل الإنتاج | أثبت سياسات RLS والترحيلات والنسخ الاحتياطي في PostgreSQL المدارة؛ لا تستخدم Database-per-Tenant في المرحلة الأولى. |
| UUID مقابل Business Code | موثق ومطبق في العقود الحالية. | **موجود — تثبيت في Data Dictionary** | قريب | يحسم الالتباس بين معرف قاعدة البيانات وكود الأصل المتداول. |
| Materialized Path للمواقع | موثق كخيار رسمي؛ SQL القديم يقدم `FullPath` مفيداً للترحيل. | **اعتماد ADR تنفيذي أولاً** | عند ترحيل PostgreSQL | لا يغير مخططاً عاملاً قبل قرار ترحيل وفحص أداء وتعليمات تحديث المسار. |
| Maker–Checker وSoD | الحذف الناعم والتدقيق موجودان؛ محرك موافقات عام غير موجود. | **اعتماد محدود ومبني على مخاطر** | V2 | ابدأ بأربع سياسات: الاستبعاد، فروقات الجرد، نقل عالي القيمة، وتعديل أصل حساس؛ لا تبنِ Engine عاماً لكل إجراء. |
| إطار ترحيل البيانات القديمة | توجد صفحة قالب استيراد، وليس خط ترحيل منضبط كامل. | **اعتماد مرتفع عند وجود بيانات حقيقية** | قبل أي استيراد فعلي | يتطلب Dry Run، Profile، تنظيف، تطابق، تقرير تسوية، وقابلية إيقاف؛ لا تعرض وضع «استبدال» عاماً في الإنتاج. |
| مراقبة عمليات الفرق الميدانية | توجد أسس Offline-first، ولا تتضح بعد لوحة مركزية لحالة الأجهزة والتعارضات. | **اعتماد V2** | بعد ربط مزامنة الجوال بالإنتاج | يضيف قيمة فعلية عند توفر أجهزة حقيقية وسجل مزامنة موثوق؛ تنفيذه الآن سيكون واجهة بلا بيانات تشغيلية. |
| Audit Intelligence وAI | توجد تحليلات ومساعد موقع L1؛ التنبؤ بالصيانة لا يملك بيانات تدريب كافية. | **اعتماد متدرج** | V2–V3 | ابدأ بتحليلات SQL قابلة للتفسير وكشف تكرار/شذوذ، ثم تحليل صور، ثم تنبؤ صيانة فقط بعد توافر بيانات تاريخية. |
| جدول SQL Server القديم | يغطي كيانات أعمال صحيحة، لكنه يعتمد Identity وجداول أحادية الجهة وحقول مكررة. | **مصدر ترحيل فقط** | عند ترحيل البيانات | تستخدمه لخريطة تحويل، لا كمخطط مستهدف. |

## قراءة مخطط SQL القديم

مخطط النظام السابق يؤكد صحة مجالات الأعمال الموجودة في AssetX: الأصول، النماذج، المواقع، الحركات، الجرد، الصيانة، الموظفون، المستخدمون، الصلاحيات، التدقيق والإعدادات. لكنه ليس مناسباً للتبني المباشر. الملاحظات التالية مهمة عند أي ترحيل:

| عنصر قديم | المقابل الحديث | قرار التحويل |
|---|---|---|
| `IDENTITY(int)` | `UUID` | إنشاء UUID جديد لكل سجل والحفاظ على المفتاح القديم في جدول استيراد/عمود `legacy_id` عند الحاجة إلى التتبع. |
| `tblAssets.FullAssetCode` | `assets.full_asset_code` | يحفظ كرمز عمل فريد ضمن الجهة، وليس كمفتاح تقني. |
| `MainLocations` و`SubLocations` | `locations` هرمية | تحويلها إلى `parent_id` ومسار مادي، مع تقرير عن المسارات المكسورة أو الدورية. |
| `InventoryResult` المخزن | النتيجة المحسوبة | لا يرحّل كمصدر حقيقة؛ يعاد احتساب النتيجة من القيم المتوقعة والفعلية، وتحتفظ القيمة القديمة فقط للمقارنة. |
| صلاحيات View/Add/Edit/Delete/Print | مفاتيح RBAC الحديثة | تعتمد الصلاحيات الخمس كقاموس تاريخي، ثم تحول إلى مفاتيح دقيقة للواجهة وAPI. |
| كلمات المرور القديمة | مصادقة حديثة | لا تنقل تجزئات أو كلمات مرور؛ تنشأ دعوات أو إعادة تعيين كلمات مرور موجهة. |
| النسخ والاستعادة في التطبيق | نسخ PostgreSQL المدارة | لا يُعاد إحياء أوامر النسخ المحلية أو الاستعادة ذات الاستبدال القسري. |

### موجة التوثيق والجاهزية — قبل أي توسع وظيفي

1. إنشاء **Documentation Index** يعرّف الوثيقة المرجعية لكل موضوع، ثم إغلاق عناصر ADL المتعلقة بـUUID، المواقع، الصلاحيات، نتائج الجرد والحذف الناعم.
2. اعتماد **NFR Baseline** يحتوي أهدافاً قابلة للاختبار للبحث، الشاشة الرئيسية، التصدير، المزامنة، الاستعادة، المراقبة، التوافر والخصوصية.
3. اعتماد **ADR تنفيذية** منفصلة لـRLS في PostgreSQL وLTREE والمزامنة، بدلاً من اعتبار العنوان في وثيقة عامة قراراً منفذاً تلقائياً.

### موجة ترحيل محكومة — فقط إذا تقرر نقل بيانات النظام القديم

ينفذ مسار Extract → Profile → Cleanse → Validate → Transform → Dry Run → Import → Reconcile. ينتهي كل تشغيل بتقرير يتضمن إجمالي المصدر، المستورد، المحدث، المتخطى، المتكرر، المرفوض، ومبرر كل رفض. لا ينفذ وضع الاستبدال في بيئة إنتاج.

### موجة V2 — قيمة تشغيلية بعد ثبات الأساس

تركز على مزامنة الميدان المرئية، ولوحة تعارضات وموافقة مخاطر موجهة. لا يوصى بمحرك موافقات عام أو اشتراك وفوترة أو تكاملات خارجية قبل استخدام فعلي يثبت الحاجة.

### موجة V3 — ذكاء وتحليلات

تبدأ بتقارير علل قابلة للتفسير: الإدارات والمواقع ذات الفروقات الأعلى، تكرار البيانات، الأصول عالية المخاطر، وجودة الجرد. لا يبدأ التنبؤ بالصيانة قبل تعريف جودة البيانات وفترة تاريخية كافية.

## ما أوصي بعدم تنفيذه الآن

لا أوصي بالانتقال إلى Microservices، أو Database-per-Tenant، أو Event Broker خارجي، أو واجهة استعادة قاعدة البيانات، أو محرك موافقات عام، أو «AI تنبئي» من دون بيانات. هذه قرارات تتطلب تكلفة تشغيلية ومخاطر أكبر من العائد الحالي.

## قرار مطلوب من مالك المنتج

الخطوة التالية المقترحة ليست برمجية: اعتماد ترتيب واحد من خيارين.

| الخيار | المخرجات | متى يفضل |
|---|---|---|
| **A — توثيق وجاهزية النشر** | فهرس وثائق، NFR، ثلاثة ADR تنفيذية، وخطة RLS/استعادة. | إذا كانت الأولوية نشر النسخة الحالية بأمان. |
| **B — ترحيل البيانات القديمة** | Profiling، خريطة تحويل، Dry Run، تقرير تسوية، وخطة استيراد محكومة. | إذا كانت الأولوية نقل قاعدة بيانات النظام السابق قريباً. |

يمكن تنفيذ الخيارين بالتتابع، لكن لا يُوصى ببدئهما معاً قبل تحديد الجهة والبيئة المستهدفة للبيانات.
