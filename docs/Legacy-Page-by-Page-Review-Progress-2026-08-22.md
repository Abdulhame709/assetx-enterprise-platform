المصدر هو `/home/ubuntu/assetx-enterprise-platform-archive-2026-08-21/legacy-reference`، ويحتوي ملفات WPF/XAML وC# القديمة. لا يُنقل كود WPF أو SQL Server حرفياً؛ تُنقل الميزات والسلوكيات المؤكدة فقط إلى Next.js/NestJS/PostgreSQL مع عقود API وصلاحيات وتدقيق النظام الجديد.

## تفاصيل مؤكدة من شاشة الأصول

تحتوي شاشة الأصول القديمة على إدارة حالة السجل (`isNewRecord`, `isDirty`, `isLoading`) وتحذر من مغادرة نموذج متسخ بخيارات حفظ أو تجاهل أو بقاء. النسخ يستخدم `Asset.CreateCopyFrom`، ينسخ البيانات التجارية المسموحة، يعيد الكمية إلى 1، ويمسح الرقم التسلسلي والباركود والأكواد النظامية قبل إنشاء الأكواد الجديدة.

توجد حماية قبل التعديل والحذف عبر `AssetProtectionHelper`، وتشمل الحركات وسجلات الجرد والصيانة ودورات الجرد النشطة. توجد أيضاً مطابقة ثلاثية عند الحفظ: دمج عند التطابق الكامل، متغير جديد عند تشابه الاسم مع اختلاف سياق الهوية، أو أصل جديد.

التعديل الجماعي يرشح حسب الكود الأساسي أو الاسم أو الموقع أو الحالة أو النوع، ثم يغير الموقع أو الحالة أو الموظف المسؤول أو الكمية أو سنة الجرد بعد عرض العدد والقيمة والتأكيد. هذه الوظيفة يجب أن تبقى خلف API ومعاملة وصلاحية وتدقيق، ولا يجوز نسخ أسلوب إدخال أرقام خام من WPF إلى الواجهة الجديدة.

تضم الميزات المتقدمة بحث التشابه بنسبة، الأسماء المتطابقة، البحث النصي، الأصول التي تشترك في الكود والاسم عبر مواقع، والتقرير الشامل. هذه ميزات مرشحة للمقارنة مع البحث والتقارير الحاليين، ولا تُنفذ قبل التأكد من عدم وجود بديل في Search/ReportBuilder.

## تفاصيل مؤكدة من لوحة التحكم القديمة

يتم تحميل البيانات عند فتح الصفحة، وتعرض اللوحة المؤشرات التشغيلية الأخيرة. دورة الجرد النشطة تُحسب من السجلات الموجودة وحالات النتيجة، مع نسبة تقدم وإجمالي المشكلات. آخر الحركات تعرض آخر ثمانية، وسجل التدقيق يعرض آخر عشرة مع المستخدم ونوع العملية والقيم الجديدة. توزيع النوع والحالة يعرض حتى ثمانية أنواع وأعداد الحالات.

## تفاصيل مؤكدة من أنواع الأصول

النوع الرئيسي يملك كوداً رقمياً يولد أول رقم متاح، مع منع تكرار الاسم والكود. النوع الفرعي يملك كوداً بصيغة هرمية، مثل `main-001` ثم `main-001-001`، ويخزن `FullPath` و`LevelNumber`. يمنع حذف الرئيسي إذا كان لديه فروع أو أصول مرتبطة، ويمنع حذف الفرعي إذا كان لديه أطفال أو أصول مرتبطة.

## قاعدة قرار مؤقتة

لا توجد إضافة تنفيذية جديدة مقررة من هذه الصفحات حتى تكتمل قراءة صفحات الجرد والتقارير والاستيراد والحركات والإعدادات والمستخدمين. الميزات التي ثبت وجودها في النظام الجديد تُسجل كمطابقة، والميزات التي لها بديل حديث لا تُكرر، والميزات ذات قيمة تشغيلية ولا بديل لها تُنقل لاحقاً كحزمة مستقلة مع اختبارات regression.

## قاعدة الجرد المؤكدة

يحسب النظام القديم النتيجة بالاعتماد على الكمية والموقع المتوقع/الفعلي والحالة. لا يجوز نقل سجل الجرد إلى الأصل مباشرة عند الإدخال؛ تبقى snapshot ونتيجة الجرد منفصلتين حتى المراجعة والاعتماد. هذا المبدأ متوافق مع تصميم AssetX الجديد ويجب الحفاظ عليه.

## صفحة النقل وسجل الحركات

تم فحص `AssetTransferView.xaml/.cs` و`AssetMovementHistoryForm.xaml/.cs`. شاشة النقل القديمة تبحث عن أصل، تعرض حالته الحالية من موقع/موظف/حالة، تملأ الوجهة بالقيم الحالية، وتغير الحقول عند اختيار إتلاف أو استغناء. التنفيذ يرسل نوع الحركة والوجهة والموظف والحالة والسبب ورقم المرجع والمعتمد والملاحظات، مع تعطيل الأصل عند الإتلاف/الاستغناء.

سجل الحركات القديم يعرض بيانات الأصل، من/إلى موقع وموظف، الحالة القديمة/الجديدة، السبب والمرجع والمعتمد ومنشئ السجل. يدعم البحث، نوع الحركة، التاريخ، الموقع الرئيسي والفرعي، الموظف، تفاصيل كاملة، CSV، والطباعة، مع مؤشرات لأنواع الحركات. واجهة AssetX الجديدة تغطي قائمة الموافقات والفلاتر والتفاصيل والتصدير والطباعة؛ المرشح الوحيد للمقارنة الإضافية هو التأكد من اكتمال كل حقول من/إلى والسبب والمرجع والمعتمد في نافذة التفاصيل، وليس إنشاء صفحة حركة ثانية.

## صفحة تقارير الأصول

تم فحص `AssetsReportForm.xaml/.cs`. يوفر التقرير القديم فلاتر الاسم والموقع الرئيسي والفرعي الهرمي مع احتساب الأبناء والنوع الفرعي والحالة والموظف والموديل والسعر والتاريخ وسنة الجرد والباركود/الرقم التسلسلي. يدعم تقريراً مخصص الأعمدة، تقريراً تفصيلياً كاملاً، تقريراً مجمعاً بمتغيرات group-by، إخفاء القيم المتكررة بصرياً، مؤشرات عدد السجلات والكمية والقيمة وعدد المواقع والأنواع، بحثاً داخل النتائج، وصف الفلاتر في الإخراج، معاينة وطباعة وتصدير وإعادة ضبط.

مصمم تقارير AssetX الحالي يغطي اختيار الأعمدة، profile، الفرز، التجميع، Count/Sum/Avg/Min/Max، CSV/XLSX/PDF، القوالب المشتركة، ووصف الإخراج. لذلك لا ينبغي إنشاء `AssetsReportForm` جديدة؛ تتم فقط مقارنة أي حقول أو مؤشرات مفقودة مع ReportBuilder الحالي.

## نافذة معاينة التقرير القديمة

`ReportPreviewWindow` كانت غلاف WPF لـ`FixedDocument/XPS` يعرض العنوان واسم المؤسسة ووصف الفلاتر ومنفذ التقرير وعدد السجلات والصفحات، ويدعم الطباعة وExcel والتكبير/التصغير والإغلاق، مع حقول توقيعات المستلم وأعضاء اللجنة ورئيسها. مصمم AssetX الحديث يولد CSV/XLSX/PDF من الخادم وتوجد معاينة/طباعة داخل صفحة التقارير، لكن توقيعات نماذج الجرد الورقية ليست جزءاً من عقد التقارير الحالي. لذلك لا تُنقل نافذة XPS أو Excel القديم؛ تبقى التوقيعات ونموذج الجرد الموقّع مرشحاً مستقلاً فقط إذا صُمم له PDF server-side وmetadata واضحة.

## ملاحظة لوحة التحكم

الكود القديم يعرض مؤشرات القيمة ودورة الجرد والحركات الحديثة وآخر التدقيق، بينما صفحة AssetX الحالية تستهلك ملخص `/assets/analytics/summary` الذي يعيد مؤشرات الأصول والتوزيعات فقط. توجد عقود قراءة أغنى في `/dashboard/*` لبعض البيانات، لكن ربطها بالواجهة يجب أن يتم لاحقاً بعد التحقق من مخططاتها وtenant isolation، وليس عبر اختلاق بيانات أو تغيير منطق التحليلات.

## أول ترحيل انتقائي بعد المقارنة

تم اختيار **إجمالي قيمة الأصول** فقط من فجوة Dashboard. السبب أن `ReportingRepository.getAssetDashboard` يحسبها فعلياً من `purchase_price * quantity` مع مرشح `tenant_id`، ولا يحتاج إلى mutation أو schema أو endpoint جديد. أضيفت قراءة اختيارية من `/dashboard/assets` إلى طبقة API الحالية، وmapping دفاعي، وبطاقة KPI مترجمة في `/dashboard`. إذا لم يتوفر العقد الغني، يبقى الملخص الأساسي عاملاً وتعرض البطاقة شرطة بدلاً من قيمة مصطنعة؛ كما لم تُفترض عملة لأن إعدادات المؤسسة المالية لم تُرحّل بعد.

### ترحيل إدارة الموديلات

بعد التحقق من `ModelsForm` اتضح أن المجال الحديث موجود في قاعدة البيانات و`ModelController` وخدمة الموديلات وصلاحيات RBAC، لكنه لم يكن معروضاً كصفحة مستقلة. لذلك أضيف مسار `/models` ضمن البيانات الأساسية، مع قراءة tenant-scoped، بحث محلي، مؤشرات عددية، إضافة وتعديل حقيقيين عبر `POST /models` و`PATCH /models/:id`. الحقول المعروضة هي الاسم والفئة الاختيارية وفق العقد الحديث؛ لم تُنسخ الشركة/المورد أو توليد الأكواد القديمة. لم يُعرض الحذف لأن backend لا يملك عملية حذف/تعطيل للموديلات، التزاماً بقاعدة عدم وجود أزرار وهمية.

هذا الترحيل لا يشمل بعد دورة الجرد أو آخر الحركات أو آخر التدقيق؛ فهي تحتاج عقود عرض/تصفية متسقة أو endpoints قراءة مستقلة، وسيتم بحثها كحزم لاحقة فقط إذا ثبتت قيمتها دون تكرار. وبذلك لا يُعد تدقيق النظام القديم مكتملاً بعد.
